# Google Sign-In and Payments

## Google Cloud setup (both account types)

1. Open https://console.cloud.google.com/ and create or select the AbangTa project.
2. In Google Auth Platform, configure Branding, Audience, and Data Access. Use your own support email. Request only basic profile/email access. If the audience is External and the app is in Testing, add the Google accounts you will test as test users.
3. Under Clients, create an OAuth client with application type **Web application**.
4. Add Authorized JavaScript origin `http://localhost:3000` and Authorized redirect URI `http://localhost:3000/api/auth/callback/google`. The redirect URI must match exactly, including the port. Use HTTPS URLs on your actual domain when deploying.
5. Set these in BOTH `.env` and `.env.local` if both files define authentication settings (Next.js local settings take precedence):

```dotenv
AUTH_URL=http://localhost:3000
AUTH_GOOGLE_ID=your-client-id.apps.googleusercontent.com
AUTH_GOOGLE_SECRET=your-client-secret
```

Keep the existing strong `AUTH_SECRET`; do not regenerate it for this setup. Never prefix these secrets with `NEXT_PUBLIC_`, commit environment files, or paste secrets into chat.

6. Restart `npm run dev`. Choose Landlord or Tenant, then Create account with Google. For an existing account, choose Sign in. A password account must first sign in with its password and use **Connect Google** in Profile. Connecting does not change the account's role or create another tenant record. Mobile-only accounts can attach their verified Google email this way.
7. Test each role with separate Google accounts, then sign out and sign in again. Test a room invitation across registration. Choosing the wrong portal must not change an existing role. Canceling Google must not create an account. Once configured, publish the consent configuration as appropriate for your real users.

The application cannot complete real Google authentication until valid credentials and the exact callback URI are configured in Google Cloud. One OAuth client serves both roles. State, PKCE, verified email checks, and signed role intent are enforced.

References: https://authjs.dev/reference/core/providers/google and https://developers.google.com/identity/protocols/oauth2/web-server

## Wi-Fi, parking, and other charges

On the property Overview, choose **Wi-Fi & parking setup**, select **Charge separately**, **Included in rent**, or **Free**, and press **Save monthly defaults**. Leave **Not applicable** for services not offered. Defaults are property-specific and charged per tenant per month, not split from a property total. Parking applies only according to each tenancy's parking setting below.

Generate monthly bill automatically prefills these saved defaults. You can change an amount, choose included/free, or select not applicable for this bill without changing the property defaults. Custom charges remain bill-specific. Saving revised defaults affects future generated bills only; existing bill snapshots are unchanged. Removing both defaults prevents these items appearing on subsequent bills. Bills are still generated by the landlord, not automatically scheduled.

### Tenant-specific parking

In Property > Tenants, each active tenancy has a Parking selector and **Save parking**. Choose:

- **Uses parking - property rate**: new bills inherit that property's parking amount/treatment. A landlord can waive it on an individual bill. Configure the property parking default before assigning this option.
- **Free parking**: a zero-amount Parking / Free item is shown, regardless of the property parking fee.
- **Not applicable**: no parking item is added.

All new and existing tenancies start at Not applicable after this migration. Explicitly assign parking to the tenants who use it. This avoids surprise charges. Historical bills are never changed automatically.

Changing the tenant in Generate monthly bill refreshes parking controls for that tenancy. Paid parking is locked out for free/non-applicable tenants, and the server rejects forged paid-parking inputs. Updating a tenancy setting affects future bills only. Assignments are tied to a tenancy, so a new lease starts without parking rather than inheriting a previous resident's setting.

### Public footer

About AbangTa, Contact us, and Follow us appear below sign-in and both portals, using the existing theme. Configure only official public details in the environment, then restart the server:

```dotenv
ABANGTA_CONTACT_EMAIL=
ABANGTA_CONTACT_PHONE=
ABANGTA_FACEBOOK_URL=
ABANGTA_TIKTOK_URL=
ABANGTA_INSTAGRAM_URL=
```

Social URLs must use HTTPS and the exact official platform host, pointing to your own profile/page. Empty or invalid values stay inactive; no placeholder destinations or invented contact details are published. These are public business details, not your personal GCash number or authentication credentials.

Only separately charged items increase the total. Included/free items have zero amount and explicit labels. Existing water/electricity metering and allocation rules are unchanged. Saved bills retain their item labels, amounts, and treatment.

## Cash and GCash (manual confirmation)

1. Landlord: in Profile, save the GCash account name and Philippine mobile number together. These details appear only on that landlord's tenants' unpaid bills. Keep them current; tenants must confirm the recipient shown in GCash before sending money.
2. Tenant: pay cash directly to the landlord, or transfer using those GCash details. Keep the GCash transaction reference and give it to the landlord.
3. Landlord: verify receipt in your own GCash transaction history or receive the cash, open the bill, and Record payment. Select the actual method and amount. GCash requires the transaction reference. Confirm receipt before submitting. A screenshot alone is not confirmation of funds received.
4. Partial payments are supported. The application refuses overpayments, reused payment submissions, and duplicate GCash references for the same landlord. One GCash transaction is recorded against one bill; ask tenants to make separate transfers for separate bills. Voiding retains the payment and reference for audit history; a voided reference cannot be reused. Correct a wrong allocation through a documented reconciliation rather than entering the same transfer twice.

No GCash API keys, checkout processing, automatic payment verification, or generated payment QR are used. The invitation QR is NOT a payment QR. Tenants cannot mark themselves paid. Existing bank-transfer/other payment history remains supported.

## Local verification

### Confirmed payment receipts

Each newly recorded, landlord-confirmed Cash/GCash payment receives an immutable receipt snapshot in the same database transaction. The landlord's bill detail and the tenant's Bills/Payment history pages show a download icon for its PDF. Partial payments receive receipts for the actual amount paid, not the whole bill. The balance shown is the balance at confirmation.

Existing payments are not silently marked confirmed by migration. On the bill detail page, the original landlord must check that the payment was received and select **Confirm and issue receipt**. This does not add another payment or change the bill balance. Bank-transfer/other records do not receive these Cash/GCash receipts.

Only the owning landlord and that payment's tenant can download. Receipt routes are private, rate-limited and not cached. Voided payments cannot download receipts; an already downloaded copy cannot be recalled and states that it becomes invalid on reversal. Snapshot names, amounts and reference remain unchanged if profile/property details change. The Noto Sans font is distributed under its included license; unsupported glyphs are preserved as explicit Unicode code points rather than silently disappearing.

### Unpaid bill reminders

Automatic in-app bill reminders start with `npm run dev` and `npm run start`. No manual reminder action, separate cron setup, browser visit or configured job secret is required for a continuously running Node server. The launcher performs its first check after 15 seconds, then checks every five minutes without overlapping its previous request. It retries temporary server/database failures and stops with the application server. No email or SMS delivery is claimed.

Only unpaid active-tenancy bills due within 72 hours or overdue are eligible. Paid/cancelled bills, archived properties/rooms, and inactive tenancies are excluded. Actual non-voided payments are rechecked under the same bill-row lock used by payment recording. Each bill AND each tenant can receive at most one reminder per 24 hours, including manual sends, competing app instances and restarts. If a tenant has multiple unpaid bills, one eligible bill is selected per day, prioritizing never-reminded/older-due bills. A new reminder marks earlier bill reminders read so notices do not accumulate. New payments dismiss old unread reminders, preventing stale balance messages. The migration carries recent delivery timestamps forward.

The local loop calls the protected `/api/jobs/bill-reminders` endpoint using a private random process secret. It is never printed, put in a URL, or sent to an external address. Each run processes at most 100 eligible bills; the shared database limits the job to once per minute across instances, with the per-tenant/bill cooldowns enforced transactionally. Manual **Send reminder** remains available but obeys the same anti-spam limits.

Keep the app server running for reminders to continue. Local reminders stop while the computer/server is off or asleep; the next run catches up without sending duplicates. Run a continuously hosted Node server in production and use HTTPS for public traffic. Running `next dev` or `next start` directly bypasses the launcher; use the npm commands. `npm run build` does not start a reminder loop or send notifications.

For serverless hosting (where no continuous Node process exists), use the hosting scheduler instead: set a strong `BILL_REMINDERS_SECRET` of at least 32 random characters and POST to `/api/jobs/bill-reminders` with `Authorization: Bearer <secret>`. Set `BILL_REMINDERS_AUTOMATIC=0` only when opting out of the built-in loop. A configured secret is optional for normal npm launches; an empty value is safely generated in memory. A nonempty weak secret is rejected. The launcher only contacts its loopback address and will not follow redirects.

PDF generation uses PDF-LIB (https://pdf-lib.js.org/) with the licensed Noto Sans font under `assets/fonts/`.

```sh
npm run prisma:migrate:prod
npm run prisma:generate
npm run typecheck
npm run lint
ABANGTA_DB_TESTS=1 npm test -- --runInBand
npm run build
```

Migrations add optional fields and item types without resetting existing data. Use a backup and a maintenance window before production migrations. All application instances must use the same MySQL database for shared rate limiting.
